TEST MACHINE
------------
  Laptop    : Lenovo 82RD, on AC power
  CPU       : AMD Ryzen 7 6800H (8 cores, 16 threads)
  RAM       : 16 GB
  GPU       : NVIDIA GeForce RTX 3060 Laptop GPU, 6 GB (driver 621.01)
  OS        : Windows 11, WSL2 Ubuntu 24.04
  WSL2      : limited to 4 logical processors and 6 GB RAM
  Toolchain : GCC 13.3.0, Open MPI 4.1.6, CUDA 12.2 (host GCC 12.4.0)

All CPU results are for 4 logical processors, not the whole CPU.
Times cover the search only (not dataset loading, or the one-time copy of the
base set to the GPU). One run per configuration unless stated.

1. SHARED MEMORY (OpenMP and POSIX threads)
-------------------------------------------
  Threads    OpenMP (s)   Speedup   Efficiency    Pthreads (s)   Speedup
  -------    ----------   -------   ----------    ------------   -------
     1         645.24      1.00x       100%          645.24       1.00x
     2         338.00      1.91x        95%          358.51       1.80x
     4         189.47      3.41x        85%          192.80       3.35x
     8         196.84      3.28x         -           192.85       3.35x

  (The 1-thread row is the serial program.)

  - Both scale well up to 4 threads, the number of logical processors available.
  - At 8 threads there are twice as many threads as processors, so there is no
    further gain. Efficiency is not meaningful for that row.
  - OpenMP and hand-written POSIX threads perform almost the same: the work is
    independent per query, so there is little to schedule.


2. DISTRIBUTED MEMORY (MPI)
---------------------------
  Ranks    Time (s)    Speedup    Efficiency
  -----    --------    -------    ----------
    1       645.24      1.00x        100%     (serial program)
    2       342.27      1.89x         94%
    4       185.64      3.48x         87%

  The 4-rank runs use `mpirun --use-hwthread-cpus`.

  - The base set is split across ranks; every rank searches its slice for all
    queries.
  - Ranks communicate once, at the end: each sends 10 distances and 10 indices
    per query to rank 0, which merges them. The amount of data is small
    compared with the computation, which is why scaling stays close to the
    shared-memory versions.


3. HYBRID (MPI + OpenMP and MPI + POSIX threads)
------------------------------------------------
  Ranks x threads    Workers    MPI+OpenMP (s)   Speedup    MPI+POSIX (s)   Speedup
  ---------------    -------    --------------   -------    -------------   -------
      2 x 2             4           189.73        3.40x         190.11       3.39x
      2 x 4             8           188.10        3.43x         189.58       3.40x
      4 x 4            16           185.89        3.47x         186.56       3.46x

  - With 4 workers (2 ranks x 2 threads) both hybrids match pure OpenMP and
    pure POSIX threads on this machine.
  - More workers than the 4 logical processors changes the time by about 2% at
    most.
  - A hybrid pays off when ranks run on separate machines, each with its own
    cores. That was not tested here.


4. GPU (CUDA)
-------------
  Batch     Thread blocks    Batches    Time (s)    Queries/s    Speedup
  -----     -------------    -------    --------    ---------    -------
    256           2             40       191.71        52.16       3.37x
    512           4             20        96.28       103.86       6.70x
   1024           8             10        47.95       208.55      13.46x
   2048          16              5        36.09       277.08      17.88x
   4096          32              3        43.55       229.62      14.82x
   8192          64              2        36.60       273.25      17.63x
  10000          79              1        27.80       359.74      23.21x

  (Thread blocks = per full batch, 128 threads each.)

  Repeat runs: 4096 -> 43.78 s, 8192 -> 36.58 s, 10000 -> 27.78 s.

  - One GPU thread handles one query, so the batch size sets how much work the
    GPU has at once. At 256 queries there are only 2 thread blocks per batch and
    most of the GPU waits.
  - From 256 to 1024 the time halves each time the batch doubles.
  - Beyond that the gains are uneven: 4096 is slower than 2048, in both runs.
    The best batch size has to be measured.
  - Sending all 10,000 queries as one batch was fastest. The two-stream
    pipeline only comes into play when there is more than one batch.


CORRECTNESS
-----------
  `make verify` repeats the exact search and compares distances with the ground
  truth:

      Recall@10 by neighbour index    : 99.93% (70 mismatches)
      Recall@10 by neighbour distance : 100.00% (0 mismatches)

  Every index mismatch is therefore a tie: a different vector at exactly the
  same distance. The full CUDA neighbour lists (batch 4096 and 10000) and the
  4-rank MPI lists passed the same distance check with 0 mismatches.


RECOMMENDATIONS
---------------
  Situation                        Use
  ------------------------------   -----------------------------------------
  NVIDIA GPU available             CUDA, with the batch size tuned
  CPU only, one machine            OpenMP, one thread per logical processor
                                   (within 2% of the fastest CPU run)
  Data too large for one machine   MPI, with OpenMP or threads inside a node
  Checking another implementation  Serial
